# Elicitation Techniques and QuestionsF

---

## 1. Individual Developers

**Technique:** Interview + Observation

**Why?**
Developers work on the code, pull requests, and issues. We need to understand their daily work and the problems they face.

**Questions:**
1. What problems do you face while working on a project?
2. What usually causes delay in your work?
3. What information would you like to see on the dashboard?
4. How should the system tell you that you are overloaded?
5. What can make an AI warning wrong?
6. Should you be able to give feedback if an AI warning is wrong?
7. Which information about your work is most useful to you?

**Observation:**
We can watch how developers work with tasks, issues, and pull requests.

---

## 2. Code Reviewers / Senior Engineers

**Technique:** Interview + Observation

**Why?**
They review code and manage pull requests. We need to understand why reviews may be delayed.

**Questions:**
1. Why do pull requests usually take a long time to review?
2. How do you check pending pull requests now?
3. What information would help you find a review problem?
4. When does a delayed pull request become a risk?
5. What should the system show when a review is delayed?
6. Are there cases where a long review time is normal?

**Observation:**
We can watch the normal code review process.

---

## 3. Engineering / Team Leads

**Technique:** Interview + Observation

**Why?**
Team leads use project information to check team progress and manage workload.

**Questions:**
1. How do you check if your team is doing well?
2. How do you know when a team member has too much work?
3. What signs show that a project may have a problem?
4. What kind of suggestions should the system give you?
5. What information do you need before following an AI suggestion?
6. What should you see first on the dashboard?

**Observation:**
We can see how team leads check progress and workload.

---

## 4. Scrum Masters / Agile Coaches

**Technique:** Interview + Brainstorming

**Why?**
They work with sprints, standups, and retrospectives. They can tell us what sprint information is useful.

**Questions:**
1. What problems usually happen during a sprint?
2. Which sprint information do you check regularly?
3. How do you know when a sprint may be delayed?
4. Which blockers should the system show?
5. What information would be useful during a daily standup?
6. What information would be useful during a sprint review?
7. What suggestions from the system could help the team?

**Brainstorming:**
We can discuss ideas for finding sprint delays, blockers, and other risks.

---

## 5. Project Managers

**Technique:** Interview + Questionnaire

**Why?**
Project Managers need to know the overall project progress, schedule, and risks.

**Questions:**
1. How do you currently check project health?
2. Which project risks are most important to you?
3. How early should the system warn you about a problem?
4. What should be included in the project report?
5. How often should you receive the report?
6. Do you want only the risk result or also the reason for the risk?
7. Which project information is most important to you?

**Questionnaire example:**
How useful would an automatic project health report be?
- ☐ Not useful
- ☐ Slightly useful
- ☐ Useful
- ☐ Very useful
- ☐ Extremely useful

---

## 6. System Administrators / DevOps Engineers

**Technique:** Interview + Document Analysis

**Why?**
They manage deployment, system settings, credentials, and connections with GitHub and Slack.

**Questions:**
1. What is needed to connect the system with GitHub?
2. What is needed to connect the system with Slack?
3. How should passwords and API keys be stored?
4. Who should be allowed to access the system?
5. What should happen if an external service is not working?
6. What security problems should we consider?
7. What information should be stored in system logs?

**Document Analysis:**
We can check GitHub API, Slack API, security, and deployment documentation.
